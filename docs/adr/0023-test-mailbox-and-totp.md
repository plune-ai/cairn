# ADR-0023: Тестова поштова скринька і TOTP для браузерних сценаріїв — окремий шов поза `BrowserGateway`, вимкнений за замовчуванням

- **Статус:** Proposed (spike BH-G1, plune-ai/cairn#205; реалізація — BH-G2, cairn#206)
- **Дата:** 2026-10-22
- **Код прототипу:** `src/mailbox/` (`types.ts`, `index.ts`, `fake.ts`), `src/totp/index.ts`; тести `tests/mailbox/`, `tests/totp/`. До жодного потоку за замовчуванням не підключено.
- **Зв'язок з іншими ADR:** [ADR-0003](0003-browser-gateway-hybrid.md) (браузер лише через `src/browser/gateway.ts`), [ADR-0005](0005-test-output-format.md) (вихід — `@playwright/test`), [ADR-0017](0017-opt-in-pipeline-passes.md) (opt-in, без прапорця — той самий байт-у-байт результат), [ADR-0020](0020-untrusted-llm-verdicts-and-data-protection.md) (дані й секрети), [ADR-0021](0021-human-authored-case-as-input-boundary-unchanged.md) (людський кейс як вхід), [ADR-0022](0022-optional-decision-layer.md) (редакція секретів у `src/decider/redact.ts`).

## Контекст

Реєстрація, скидання пароля, запрошення і 2FA майже завжди проходять через лист (посилання або код) чи TOTP. Без цього агент зупиняється на найважливіших потоках, а поширена порада — «вимкніть це на тестовому оточенні» — не підходить командам, які тестують справжній потік.

Як сьогодні виражається крок. Браузерний шар знає лише три дії (`Action` у `src/browser/types.ts`): `navigate`, `click`, `fill`; усе інше (читання листа, обчислення коду) в нього не вміщається і **не повинно**: gateway — це про сторінку, а не про сторонні канали. Вихід Cairn — тест `@playwright/test` (ADR-0005), а людський кейс лишається текстом кроків (ADR-0021). Отже, потрібні дві речі: (1) під час прогону агента — виклики поза браузером, результат яких потрапляє в `fill`/`navigate`; (2) у згенерованому тесті — той самий виклик у вигляді звичайного коду.

## Рішення

**Окремий шов `src/mailbox/` + `src/totp/`, що існує лише тоді, коли кейс/конфіг просить про нього; на `BrowserGateway` він не впливає. Усе, що приходить з листа, вважається недовіреним і секретним.**

### 1. Інтерфейс провайдера скриньки

```ts
interface MailboxProvider {
  readonly name: string;
  createAddress(runId: string): Promise<string>;   // одна унікальна адреса на прогін
  list(address: string): Promise<MailMessage[]>;
  cleanup(address: string): Promise<void>;
}
```

Провайдер навмисно мінімальний — лише «адреса, список, прибрати». Усе спільне (очікування, відбір, витяг) живе один раз над ним і не залежить від провайдера:

- `waitFor(provider, address, { subject, from, timeoutMs, intervalMs })` — опитування з паузою; типово 60 с / 3 с; перемагає **найновіший** лист, що збігся (регістронезалежна підстрічка теми/відправника). Таймаут — помилка **без вмісту листів**.
- `extractLink(msg, contains?)` — перше `http(s)`-посилання або перше, що містить підрядок (наприклад `/verify`).
- `extractCode(msg, pattern?, length = 6)` — окреме число з `length` цифр (довші числа, як-от номер замовлення, ігноруються) або перша група власного регулярного виразу.

Перший провайдер — **Mailsac** (REST, ключ у `MAILSAC_API_KEY`; заголовок `Mailsac-Key`). Деталі ендпойнтів уточнюються в BH-G2 за актуальною документацією — у цьому спайку живий виклик не виконувався (див. PR). Далі — IMAP/будь-який API через той самий інтерфейс. Для тестів — `FakeMailbox` (пам'ять, `deliver()` імітує продукт, що надсилає лист).

**Гонки і чистка.** Адреса на прогін: `cairn-<runId>-<n>@<домен>`; сценарії одного прогону ділять її, різні прогони — ніколи. `cleanup` викликається в `finally` завершення прогону (також при падінні); на тестових доменах Mailsac додатково діє їхнє автовидалення, але на нього не покладаємося.

**Приватність скриньки.** Публічні адреси загальних доменів поштових сервісів можуть бути читабельні кожному, хто знає ім'я. Тому адреса на прогін — випадковий невгадуваний суфікс, а для листів з персональними даними — окремий (приватний/власний) домен. Це умова для BH-G2.

### 2. TOTP (RFC 6238)

- Секрет — **base32 у змінній середовища**, у кейсі/конфігу фігурує лише **ім'я** змінної (`secretFromEnv(name)`); значення не пишеться ні в кейс, ні в звіт.
- Генерація: HMAC-SHA1 (за потреби SHA-256/512), 6 цифр, період 30 с. Перевірено на векторах RFC 6238 (додаток B, усі три алгоритми, 8 цифр).
- **Межа 30-секундного вікна.** Код, прочитаний за секунди до кінця вікна, може протухнути, поки сервер його перевіряє. `freshTotp` у таких випадках (залишок < `minRemainingMs`, типово 3 с) **чекає** початку наступного вікна й повертає код нового вікна — ніколи не віддає код, що ось-ось закінчиться. Максимальна затримка — залишок вікна (≤ 3 с). Сервери, що приймають сусіднє вікно (±1), це не ламає.
- Повторний ввід після відмови: один повтор з кодом наступного вікна, не більше; безкінечних циклів немає (захист від блокування облікового запису).
- Годинник: використовується локальний; перекіс годинника більше ~30 с — відома межа; лікується NTP на раннері, не кодом.

### 3. Що логуємо, що редагуємо

- У лог іде лише `describeForLog`: відправник без локальної частини (`***@домен`), тема, **без тіла**. Адреса, посилання, коди і TOTP-секрет — у списку секретів для наявного `redact()` (`src/decider/redact.ts`); це той самий механізм, що й для решти секретів, нового не вигадуємо. Значення, одержані з листа (посилання з токеном, код), реєструються як секрети в момент витягу — тож їх не буде ні в `report.json`, ні в артефактах, ні в журналі сесії, ні в тексті помилок.
- Тіло листа не зберігається на диск і не передається в LLM. Агент отримує лише **покажчик** («посилання знайдено», «код знайдено»), а саме значення підставляє виконавець кроку.
- Згенерований тест читає секрет і адресу з `process.env`/runtime, а не з літералів у файлі.
- Знімки екрана сторінок, де видно код/адресу: відома межа; зменшується тим, що код вводиться й одразу витрачається.

### 4. Як це пише автор сценарію і коли діє агент

Для автора — три дії, що виконуються поза браузером, і плейсхолдери в звичайних кроках:

```
mailbox.create                      → {{mailbox.address}}
fill  Email  ← {{mailbox.address}}
mailbox.waitFor  subject: "Підтвердіть", from: "noreply@"   (timeout 60s)
mailbox.extractLink  contains: "/verify"   → {{mailbox.link}}
navigate {{mailbox.link}}
totp.code  secret: env:TOTP_SECRET   → {{totp.code}}
fill  Code  ← {{totp.code}}
```

Плейсхолдери розкриваються **пізно**, у момент виконання кроку, і лише всередині `fill`/`navigate`. Для людського кейсу (ADR-0021) текст кроку лишається природною мовою («Ввести код з листа»); виконавець за ключовими ознаками (лист/посилання/код/одноразовий пароль) пропонує відповідну дію.

**Коли застосовує агент.** Тільки якщо ввімкнено шов (конфіг/прапорець) **і** виконується хоч одна ознака: поле, що просить код/OTP/2FA; сторінка/текст «перевірте пошту», «надіслали лист», «підтвердіть e-mail»; крок кейсу прямо згадує лист чи код. Без ввімкнення агент ці поля не заповнює і чесно позначає крок як «потребує пошти/OTP» (поведінка сьогодні). Рішення «чи треба» не віддається LLM довіреною відповіддю: це правило за ознаками, а LLM лише допомагає розпізнати поле (ADR-0020).

### 5. Чого НЕ підтримуємо і що радимо

| Потік | Статус | Що радимо |
|---|---|---|
| SMS-коди | Не підтримуємо: потрібні реальні номери, вартість, непередбачуваність, чужі дані | Тестове оточення з фіксованим кодом для тестових номерів, або вимкнений SMS-крок для тестового тенанта; для телефону — окремий ручний кейс |
| Push-підтвердження, апаратні ключі, passkeys | Не підтримуємо | Тестовий акаунт без цього фактора або bypass для тестового тенанта |
| CAPTCHA | Не підтримуємо і не обходимо | Вимкнути на тестовому оточенні або тестовий ключ провайдера |
| Листи на корпоративну пошту, реальні скриньки людей | Не підтримуємо (ризик ПД) | Лише виділена тестова скринька/домен |
| Вхід із чужим секретом TOTP з продакшну | Не підтримуємо | Окремий тестовий акаунт із власним секретом |

## Наслідки

- Опційність: без прапорця Cairn працює байт-у-байт як раніше (ADR-0017); нових залежностей немає (`node:crypto`, `fetch`).
- Нова поверхня ризику — секрети й ПД з листів; закрита правилами розділу 3, а не довірою.
- Затримка до 3 с на межі TOTP-вікна — свідома ціна надійності.
- Mailsac (і подібні) — зовнішня залежність прогону; недоступність дає зрозумілу помилку «mailbox: …», а не «невідома помилка кроку».
